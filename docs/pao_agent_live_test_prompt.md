## 通用判定标准

- 事实必须能追溯到本项目配置、节点库、仿真库、工具结果或本轮日志；静态分析和机理推测不得写成已经验证的仿真结论。
- 对话显式算法优先于YAML；不能把GA偷偷换成NSGA-II、把不可用算法偷偷换成random。
- 在全部预算与目标明确前只澄清；具体执行计划经过Gateway校验、预览、批准后才能触发Aspen。
- 短回复正确绑定等待字段；更正及时生效；不丢原目标、算法、组分和已填写预算；修改后旧审批失效。
- 百分数和分数等值转换正确；不直接比较质量分数与摩尔分数；不把上限、区间或近似值误转成精确下限。
- 代数包含初始种群。种群4、2代应计划8次评估；代数不是评估次数。预算不足一个完整种群时应解释并澄清。
- 不支持的功能应给出可理解的限制或下一步，不能崩溃、伪造执行成功或重复索要已确认字段。
- 明确目标格式错误、字段缺失、证据不足、依赖不可用、网络超时、仿真失败和清理未确认之间的区别。
- 不应出现未处理堆栈、无意义的“请明确字段”循环、无状态丢失原因的内部错误。对于设计上必须停止的异常，要有原因、审计和已执行结果的保留。
- 测试预期应依据产品契约和当前能力。不要为了让断言通过，把合理的澄清或正确拒绝改成执行。

T007：`现在的目标和约束分别是什么？`——数值与旧注释冲突时解释。

## 异常与稳健性补充

- 不故意杀死用户Aspen或破坏当前配置。缺失文件/库、非法值等异常尽量用独立副本触发。
- 网络/API故障自然出现时记录并测试恢复；不要把故障算PASS，也不要连续无限重试。相同确定性错误先定位代码，网络错误最多少量有界重试。
- 需要故障注入时，另建清楚标注的自动回归测试；不能把注入测试统计成真实LLM或真实Aspen完成。
- 对超时且执行状态未知的动作停止派发，不自动重放；检查本轮拥有的进程、线程和模型副本，保留证据。不要终止用户原有进程。
- 原模板含全模型manifest自动扫描；若成为瓶颈，可在独立验收配置明确关闭可选全树遍历，保留标量输出、目标/约束和收敛检查，并在报告中写清配置差异。

优先修复协议和状态管理，不用固定关键词回答替代LLM；可以规范化有确定含义的别名和数值格式。
